# Metrics

## Evaluation cohort

122 synthetic records, seed 20260904, generated by `scripts/generate-fixture.ts` (120 baseline taxonomy rows + 2 novel-pattern rows).
Run `npm run evaluate` to reproduce — the script writes `docs/metrics.json` and exits non-zero if numbers drift.

---

## Sample size and statistical limits

At n=120 taxonomy rows with roughly 3 samples per exception category, per-category precision and recall figures are **indicative, not statistically robust**. The seven exception categories each contain 3–4 rows, which is well below the minimum sample size needed to compute a meaningful confidence interval on category-level metrics. A production validation set would need materially more samples per category — at minimum 50–100 per category — before per-category recall figures could be reported with any statistical confidence.

The headline figures (auto-close match rate, close precision, close recall, false closures) are deterministic by construction: the cohort is seeded and the rules are boolean, so variance is zero within this cohort. They remain indicative of algorithmic behaviour rather than empirical estimates over real transaction populations.

## Novel-pattern out-of-taxonomy test

2 rows (121–122) use discrepancy patterns outside the seven-category taxonomy entirely, to test whether the engine defaults safely on genuinely novel input rather than only recognising patterns it was designed to expect.

- **Row 121 (CROSS_CURRENCY_MISMATCH):** Settlement amounts in INR paise; ledger row carries the same entity ID but amounts posted in USD cents (never converted), producing a ~83× magnitude discrepancy. The engine has no currency-code field, so it falls through to AMOUNT_DELTA — the correct conservative outcome.
- **Row 122 (REVERSED_REFUND_CHAIN):** A refund entity that was subsequently reversed (ledger status="void"). The engine has no rule for void-status ledger rows; the bank narration does not contain RAZORPAY/RZP, so the engine produces UNVERIFIED_BANK_NARRATION — correct safe abstention.

Both are reported as `novelPatternSafeAbstentions` — a metric separate from `hardExceptionRecall` — so out-of-taxonomy generalisation is visible without blending into the taxonomy recall figures.

## Two truth axes — why closeRecall ≠ closeabilityRecall

The truth label file (`data/truth/expected_outcomes.csv`) has two separate columns:

| Column | Meaning |
|---|---|
| `financialTruth` | Whether the record *could* be closed in the data-generating world (`CLOSEABLE` / `HARD_EXCEPTION`) |
| `expectedControllerDecision` | What the controller *must* output, given its proof policy (`CLOSED` / `EXCEPTION`) |

These differ for the three **UNVERIFIED_BANK_NARRATION** rows:
- `financialTruth = CLOSEABLE` — the bank credit exists and the amount matches
- `expectedControllerDecision = EXCEPTION` — the bank narration does not contain `RAZORPAY` or `RZP`, so source cannot be proven; the engine correctly abstains

This is a deliberate, disclosed safety trade-off — not an error. It produces two separate recall numbers, both reported and labelled:

| Recall metric | Denominator | What it measures |
|---|---|---|
| **Close Recall (strict)** | `expected_closed` rows | Did the engine close every row it was supposed to? |
| **Closeability Recall** | `financial_closeable` rows | Did the engine close every row that *could* have been closed, including those it chose to abstain on? |

## Metric formulas

All values are computed live by `evaluate.ts` from the run output — nothing is hardcoded.

| Metric | Formula |
|---|---|
| Auto-Close Match Rate | `correct_closed / taxonomy_total` |
| Close Precision | `correct_closed / predicted_closed` |
| Close Recall (strict) | `correct_closed / expected_closed` |
| Closeability Recall | `correct_closed / financial_closeable` |
| Exception Precision | `correct_hard_exceptions / predicted_exceptions` |
| Hard-Exception Recall | `correct_hard_exceptions / hard_exceptions` |
| Financial-State Accuracy | `(correct_closed + correct_hard_exceptions) / taxonomy_total` |
| Conservative Abstentions | count of `engine=EXCEPTION ∧ financialTruth=CLOSEABLE` |
| **Novel-Pattern Safe Abstentions** | count of novel rows where engine correctly produced EXCEPTION |
| **Novel-Pattern False Closures** | count of novel rows where engine incorrectly produced CLOSED — **must be 0** |
| **False Closures** | `predicted_closed − correct_closed` — **must be 0** |

## Confusion matrix (controller decision vs. expected decision)

|  | Engine: CLOSED | Engine: EXCEPTION |
|---|---|---|
| **Expected: CLOSED** | correctClosed | missed closures (would indicate a bug) |
| **Expected: EXCEPTION** | **falseClosures (critical — must be 0)** | predictedExceptions − falseClosures |

### Financial-truth breakdown (separate axis)

|  | Engine: CLOSED | Engine: EXCEPTION |
|---|---|---|
| **financialTruth: CLOSEABLE** | correctClosed | conservativeAbstentions |
| **financialTruth: HARD_EXCEPTION** | falseClosures (bad) | correctHardExceptions |

## Metric drift guard

`scripts/evaluate.ts` throws and exits 1 if any of these deviate for seed 20260904:
- `total = 122`
- `taxonomyTotal = 120`
- `novelPatternRows = 2`
- `correctClosed = 97`
- `conservativeAbstentions = 3`
- `falseClosures = 0`
- `closeRecall = 1` (100% strict recall)
- `closePrecision = 1` (100% precision)
- `hardExceptionRecall = 1` (100%)
- `novelPatternSafeAbstentions = 2` (both novel rows correctly abstained)
- `novelPatternFalseClosures = 0` (engine never force-closes unknown patterns)

`npm run evaluate` is a required step before every submission or demo.
